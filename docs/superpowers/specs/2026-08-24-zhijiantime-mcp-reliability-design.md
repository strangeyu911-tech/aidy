# 指尖时光 MCP 可靠调用与主动监督设计

## 背景与根因

CyberBoss 已通过 `CYBERBOSS_MCP_SERVERS_FILE` 将指尖时光 STDIO MCP 注入 Codex app-server。诊断确认了三件事：

- 指尖时光 MCP 能正常初始化并列出 9 个工具。
- 当前微信绑定线程可以通过 app-server 调用 `zhijiantime.list_schedules` 并读取真实日程。
- 出问题的对话中没有发生任何 MCP 工具调用；模型在未探测工具的情况下自行断言“当前会话没有暴露指尖时光 MCP”。

因此主要故障是模型使用策略缺失，而不是 MCP 注册或 bridge/session 传递失败。现有外部 MCP 配置还缺少必需启动、超时和细粒度自动批准能力，导致失败时可能继续运行，并且只读查询会产生不必要的审批摩擦。

## 目标

1. 用户询问指尖时光计划、待办、概览或统计时，模型先调用对应 MCP 只读工具，再根据结果回答。
2. 模型不得在未进行真实工具调用的情况下声称指尖时光不可用、未挂载或未暴露。
3. 四个只读工具可自动执行：
   - `list_schedules`
   - `list_todos`
   - `get_daily_overview`
   - `get_period_stats`
4. 写工具继续经过现有微信审批链路：
   - `create_schedule`
   - `create_todo`
   - `update_schedule`
   - `update_todo`
   - `complete_item`
5. 指尖时光被配置为必需服务器时，初始化失败必须显式阻止线程启动或恢复，不允许静默降级。
6. 现有未配置外部 MCP 的部署保持原行为。
7. 每次随机查岗前读取当天指尖时光日程和待办，优先监督尚未完成、已到时、逾期或临近开始的安排。
8. 当天没有日程或待办时，主动要求用户用指尖时光做计划，并让用户约定一个明确的跟进时间。
9. 到约定时间后重新读取指尖时光；如果仍无计划，要求用户立即完成或重新约定时间，形成持续闭环。
10. 规划催促和事项催促根据当天状态及最近进展变化话术，不机械重复同一句话。

## 非目标

- 不把指尖时光工具重新代理或复制到 `cyberboss_tools`。
- 不改变指尖时光 MCP 服务本身及其认证存储。
- 不自动批准任何写操作。
- 不为所有第三方 MCP 自动推断读写权限；自动批准必须由本地配置显式列出。
- 不在没有用户明确时间承诺时替用户虚构一个计划时间。
- 不把一次随机查岗直接等同于发送消息；当天安排均完成且没有其他跟进理由时，模型仍可选择不打扰。

## 设计

### 外部 MCP 配置模型

扩展 `CYBERBOSS_MCP_SERVERS_FILE` 中每个服务器的可选字段：

```json
{
  "name": "zhijiantime",
  "command": "D:\\Node_js\\node.exe",
  "args": ["D:\\指尖时光MCP\\指尖时光MCP\\dist\\src\\index.js"],
  "required": true,
  "startupTimeoutSec": 20,
  "toolTimeoutSec": 60,
  "autoApproveTools": [
    "list_schedules",
    "list_todos",
    "get_daily_overview",
    "get_period_stats"
  ]
}
```

`resolveAdditionalMcpServerConfigs` 负责校验并保留这些字段。布尔值必须是布尔类型，超时必须是正整数，工具名必须是非空字符串。无效配置在 app-server 启动前报出包含服务器名和字段名的错误。

`buildCodexMcpConfigArgs` 将其映射为 Codex 配置覆盖：

- `mcp_servers.<name>.required`
- `mcp_servers.<name>.startup_timeout_sec`
- `mcp_servers.<name>.tool_timeout_sec`
- `mcp_servers.<name>.tools.<tool>.approval_mode="auto"`

未声明的可选字段不生成覆盖值。`cyberboss_tools` 继续自动批准自己的项目内工具，保持现有行为。

### 微信线程工具使用策略

在 `templates/weixin-operations.md` 加入以下稳定行为规则：

- 当用户询问已连接应用中的数据，或询问模型能否访问该应用时，先使用相关只读工具验证。
- 对指尖时光计划、日程、待办、每日概览和统计，优先调用对应 `zhijiantime` 工具。
- 只有工具真实返回失败后，才能向用户说明不可用；说明应基于实际错误，不得猜测 bridge、session 或工具暴露状态。
- 查询成功时直接给出结果，不向用户描述 MCP、工具名或内部调用步骤。

规则进入新线程的 opening instructions，也能通过现有 instruction refresh 流程应用到已绑定线程。

### 当天安排快照与主动监督

新增一个边界清晰的指尖时光当天监督组件。它复用现有 `ZhijiantimeClient`，但不依赖模型自行决定是否查询，负责在随机查岗和固定规划检查点派发前读取当天日程与待办，并生成结构化监督上下文。

当天快照至少包含：

- 本地日期和读取时间。
- 日程与待办总数。
- 未完成项目，包含类型、标题、全天标记、开始和结束时间。
- 已完成数量。
- 按“逾期或已到时、临近开始、全天或无具体时间、未来安排”划分的优先级。

随机查岗派发前必须刷新快照：

- 有未完成项目时，将最高优先级项目及当天完成概况加入内部 check-in prompt，要求模型结合最近对话自然追问，不暴露内部结构。
- 当天项目全部完成时，将完成状态加入 prompt，由模型决定简短肯定或安静，不继续催已完成事项。
- 读取失败时只记录真实失败并生成“本次无法核对”的内部上下文，绝不能把失败解释为当天没有计划。

现有带具体开始时间的指尖时光检查点继续负责到点提醒；新增的随机检查覆盖全天安排、无具体时间待办、错过固定检查点后的复查，以及完成状态变化。两条链路读取同一真实状态，已完成项目不会再次被催。

### 无计划时的约定与复查闭环

新增按本地日期持久化的 `zhijiantime-daily-supervision.json`。文件只保存当前本地日期的记录；日期变化时用新一天的 `unseen` 记录替换旧记录。状态字段为：

- `unseen`：当天尚未检查。
- `awaiting_commitment`：已发现当天无安排，正在等待用户给出明确计划时间。
- `followup_scheduled`：用户已经约定时间，固定检查点已建立。
- `planned`：重新读取后确认当天已有日程或待办。

记录同时保存 `date`、`lastPromptAt`、`followupDueAt`、`checkpointId` 和 `updatedAt`。状态按真实 MCP 快照校正：任何时候读到至少一条当天安排即进入 `planned`，并把仍待执行的同日规划检查点标记为 `skipped/planning_created`；如果用户随后删除全部安排，则下一次检查进入 `awaiting_commitment` 并重新发起无计划流程。

无计划闭环如下：

1. 第一次发现当天为空时，把状态设为 `awaiting_commitment`，发送一条简短但明确的消息，要求用户用指尖时光做计划，并回答一个具体跟进时间。
2. 用户没有给时间且忽略消息时，保持 `awaiting_commitment`。下一次随机查岗继续追问具体时间，但必须结合上下文换一种简短说法，不能复制上次话术。
3. 当状态为 `awaiting_commitment` 且用户回复可解析的明确时间时，创建 canonical id 为 `zhijiantime:daily-planning:<date>` 的固定检查点，将状态改为 `followup_scheduled`。同日新的时间承诺会 supersede 旧检查点，保证只有一个有效跟进。
4. 固定检查点到期派发前重新读取当天数据。若已有安排，状态改为 `planned`，回复确认并让后续监督使用这些真实安排。
5. 若仍为空，明确指出尚未制定计划，要求用户现在完成或重新给出一个具体时间，状态回到 `awaiting_commitment`。
6. 用户再次给出时间后重复步骤 3–5，直到状态成为 `planned`。跨进程重启后从持久化状态和固定检查点继续。

规划检查点只负责监督用户在指尖时光中建立计划，不自动替用户创建日程或待办，因此不会绕过写操作审批边界。

### 启动与线程数据流

1. CyberBoss 桌面控制器读取 `.env`、外部 MCP JSON 和当天监督状态。
2. `RuntimeSupervisor` 将服务器命令、必需状态、超时和逐工具审批策略转换成 Codex `-c` 参数。
3. app-server 初始化 `zhijiantime`。若 `required=true` 且初始化失败，线程启动或恢复返回明确错误。
4. 指尖时光同步服务定期刷新当天安排，并维护具体时间事项的固定检查点。
5. 随机查岗或“今日规划”固定检查点到期前，当天监督组件重新读取指尖时光并生成最新监督上下文。
6. 微信消息进入已绑定 Codex 线程；处于 `awaiting_commitment` 时，用户给出的明确时间会建立或替换同日规划检查点。
7. 模型依据监督上下文及线程操作指令选择行动；用户直接询问数据时仍可调用只读 MCP 工具。
8. 四个只读工具自动执行；写工具仍产生 `mcpServer/elicitation/request`，由现有微信审批处理。
9. 模型基于真实状态给出简短微信回复，或在没有必要打扰时保持安静。

### 错误处理与可观测性

- JSON 不可读、字段非法或服务器名重复时，在启动阶段失败，不创建部分配置。
- 必需 MCP 启动失败时保留 Codex 返回的服务器启动错误，并由现有桌面运行状态显示为错误。
- 只读工具调用失败时，模型可以告知用户本次查询失败及可执行的下一步，但不能把一次调用失败泛化为“该会话没有 MCP”。
- 随机查岗读取失败时不更新当天规划状态，也不发送“你还没做计划”之类未经数据支持的催促。
- 同日规划检查点使用固定 canonical id；重新约时间会取代旧检查点，不产生并行重复催促。
- 不在日志或用户回复中输出认证令牌、完整环境变量或敏感请求参数。

## 测试

### 单元测试

- 外部 MCP 配置正确保留并规范化 `required`、两个超时和 `autoApproveTools`。
- 无效布尔值、非正超时和空工具名被拒绝。
- 生成的 Codex 参数仅自动批准显式列出的四个只读工具。
- 五个写工具不出现 `approval_mode="auto"`。
- 未提供新字段的旧配置生成结果与当前行为一致。
- 微信操作指令包含“先调用再判断”和“不得猜测不可用”的规则。
- 当天快照正确区分未完成、已完成、逾期、临近、全天和无具体时间项目。
- 随机查岗会使用最新快照，不再催促已完成项目。
- 空白当天从 `unseen` 进入 `awaiting_commitment`，不会被误标为 `planned`。
- 等待承诺时的明确时间回复会创建唯一的同日规划检查点；重新约时间会 supersede 旧检查点。
- 规划检查点到期时，有计划进入 `planned`，仍为空则回到 `awaiting_commitment`。
- MCP 读取失败不改变规划状态，也不会生成无计划断言。
- 持久化状态在进程重启后能够恢复。

### 集成验证

- 直接连接指尖时光 MCP，确认 9 个预期工具可列出。
- 通过 CyberBoss app-server 和当前绑定线程调用 `list_schedules`，确认返回结构化数据。
- 创建不绑定微信的临时 Codex 线程，询问当天指尖时光计划，确认出现 `zhijiantime` 只读工具调用且得到基于真实数据的回答。
- 验证一个写工具仍触发审批请求，不实际提交写操作。
- 临时使用不可启动的必需 MCP 配置，确认线程启动明确失败；测试结束后恢复真实配置。
- 使用空白当天执行随机查岗，确认微信消息要求用户用指尖时光做计划并给出具体跟进时间。
- 模拟用户给出时间并触发到点复查，分别验证“已有计划”和“仍为空”两条路径。
- 使用含全天安排、无时间待办、已完成事项和逾期事项的当天数据，确认随机查岗只监督正确目标。

## 发布步骤

1. 更新代码、模板、示例和测试。
2. 更新本地 `.mcp-servers.local.json`，仅自动批准四个只读工具并设置 `required=true`。
3. 运行相关单元测试与完整测试集。
4. 通过桌面控制器安全重启 CyberBoss，使 app-server 重新加载命令行 MCP 配置。
5. 刷新当前微信绑定线程的 instructions。
6. 执行只读端到端查询并确认微信侧回答来自真实指尖时光数据。
7. 执行一次随机查岗数据注入验证；若测试日期为空，再验证约时间和到点复查闭环。

## 验收标准

- 在微信中问“我今天指尖时光上有什么计划”时，CyberBoss 无需审批即可读取并回答真实数据。
- 在微信中问“你能读取指尖时光吗”时，CyberBoss 会先做只读验证，不再无依据地回答“不能”或“没暴露”。
- 创建、修改、完成指尖时光项目仍必须获得用户批准。
- 指尖时光 MCP 不可启动时，系统给出明确故障，不以缺少工具的降级线程继续工作。
- 每次随机查岗都以当天最新日程和待办状态为依据，已完成事项不会继续被催。
- 当天无安排时，CyberBoss 会要求用户用指尖时光做计划并给出明确跟进时间；到点仍为空会继续要求立即完成或重新约时，直到计划建立。
- 同一事项和同一规划阶段不会机械重复固定话术，也不会存在多个并行的同日规划检查点。
