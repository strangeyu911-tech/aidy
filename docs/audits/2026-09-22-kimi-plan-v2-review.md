## 2. 新发现

### V3｜路线 A 的缓解措施瞄错对象（决策级）

v2 第 3 步写：路线 A 的代价是模式污染，「用 prompt 设计缓解（如 system turn 输出后由适配层过滤 JSON、只留自然语言 send_message 内容）」。但：

- **送达侧本来就只发自然语言**。`stream-delivery.js:1070-1099` 把系统回合的 JSON 动作解析后，只取 `action.message` 交给 channel —— 从来没有把 JSON 发给用户。这条"缓解"当前就是既有行为，等于没缓解任何东西。
- **真正的污染在共享会话转录，而且是输入侧**。路线 A 合并 scope 后，系统回合的**输入**（`buildSystemInboundText` 生成的「SYSTEM ACTION MODE…」+ `Trigger:` 正文 + 富化的内部块，见 `system-message-dispatcher.js:44-61`）与**输出的原始 JSON**都会落进用户会话记录，并在此后每个用户回合被重放。
  证据：早前的运行时审计读到的会话 jsonl 里就有 **6 段重复的 Trigger 正文** —— 证明提示词正文确实入转录。
- **当前 runtime 没有删除/裁剪转录的通道**（ACP 只有 new/resume/prompt）。所以缓解手段只剩：重建会话（`startFreshThreadDraft` 会丢用户历史）或把系统提示压到极短。

> ⇒ 路线 A 的代价不是「prompt 可缓解」，而是**结构性的、以丢历史为代价才能清除**。裁决 §6 第 1 项前必须知道这一条；否则是重犯 v1 那种「把不可落地/代价被低估的方案当成保守选项」的错误。

### V1｜A2b 的落点是竞态，且与既有机制重叠

- `app.js:393-398`：`flushPendingInboundMessages()` 与 `flushPendingSystemMessages()` 在**同一个 `Promise.all` 里并发执行**。而 `flushPendingInboundMessages` 在派发前就把 draft 从 `pendingInboundByScope` 删掉（`:1231`）。
- 因此 A2b 想用的判据（主动消息派发前检查 `hasPendingInboundMessage`，`:1208`）处在**竞态**中：并发下主动侧可能读到"无待发用户消息"（入站侧已 pop），退避随机失效。
- 而且**已有部分优先级机制**：`:396` 传 `skipCheckin: messages.length > 0`（本轮 poll 有用户消息时不发 checkin，并在 `:1380-1383` requeue）。
- ⇒ A2b 必须同时规定两件事：① 两个 flush **串行化**（先入站、后主动）；② 与既有 `skipCheckin` 是**合并还是替换**。否则实现出来要么是竞态，要么两套机制互相打架（双重退避 / 双重放行）。

### V2｜A2b 覆盖不到事故的实际分支

- 事故时序：18:23:27 主动 turn 已开始派发 → 18:23:47 `hi` 到达 → 被 `isTurnDispatchBlocked`（`:771-785`，判 `threadState.status === "running"`）挡下并缓冲（`:1051-1054`）。
- A2b 只能覆盖「主动消息仍在队列中、用户消息已缓冲」的窗口；**已经进入在飞的主动 turn 无法让位** —— 这一点是计划自己声明的（v1 D3「在飞 turn 不可抢占」）。
- ⇒ A2b 是"缩小窗口"，不是"消除症状①/④"。应显式写进 §5 边界，否则 A2b 读起来像症状已解决。

### V4｜A1 退化为不可验收的占位断言

v1 的 A1 是可测的（「用户回合 prompt 中能读到当天已发出主动消息的**已剥离内部块的**摘要」）；v2 改成「RC1 路线落地后：用户回合不再重新打招呼（**路线确定后细化**）」。A1 是全计划**唯一对着用户可感症状**的断言，它一空，第 3 步就没有验收标准。建议按选定路线写死判据（若选 3.5：注入文本须含当天主动消息、不含任何内部块前缀；若选路线 A：用户回合能引用该系统回合的发送内容）。

### V5｜A6 用例从 4 组缩到 3 组

v1 有「「我8点前把指尖时光填好」正常建立」这一显式意图 + 时间正例，v2 未保留。这恰是**最常见的真实表述形态**，建议补回。

### V6｜A5 没有写落点

A5 要改的模板文本位于 `daily-supervisor.js:293-312`（random 指令）与 `:314-329`（planning_followup 指令），外加 `:132` 的 announcement。v2 只在第 4 步提了 `:132`，A5 本身无落点。

## 3. 我的建议（供 §6 第 1 项裁决参考，非结论）

三个选项的**真实代价**对比（把 V3 计入后）：

| 选项 | 可落地 | 代价 |
|---|---|---|
| **A1 路线 A（合并 scope）** | ✅ 当前 runtime 可做 | 系统回合的提示正文与 JSON 永久进入用户会话转录，**当前无清除通道**，只能重建会话（丢历史） |
| **A2 先做 3.5 注入缓解** | ✅ 现成追加点（`app.js:704-727`） | 低。需自带频率闸门（避免每回合重复注入）+ 注入前剥离内部块（D5） |
| **A3 不动，等 runtime 支持路线 B** | ❌ 依赖外部 | 症状 ①/②/④ 全部保留 |

我的读法：**A2 的性价比最高**（唯一不要求接受结构性污染的选项），路线 A 值得单独立项评审 —— 因为它真正的门槛不是"改多少代码"，而是"能不能接受用户会话历史被机器指令永久污染"。
