## 3. 分阶段修复计划（根因优先）

### 第 1 步｜RC3 富化幂等 + 重试剥离（P0，落点最清晰、风险最低）
- **落点**：`daily-supervisor.js`（`appendInternalContext`）、`app.js`（`scheduleSystemMessageRetry`）。
- **做法**：`appendInternalContext` 幂等化——追加前先剥离文本中已存在的内部块（`[Zhijiantime …]` / `[CyberBoss supervision note]` 等已知前缀到块尾），再追加当前块。**单点覆盖两条重入队路径**，顺带清理历史队列残留，不依赖新增标记字段。备选叠加：指纹标记（需刷新数据的场景用"替换"而非"追加"）。
- **风险**：低。剥离须按"已知块前缀 + 边界"精确匹配，勿误伤用户正文。
- **验证**：A3（连续富化 3 次块计数恒 1；路径 B 重试序列文本不增长；补路径 B 单测）。

### 第 2 步｜RC2 random 过期即弃（P0，几行代码，政策对齐）
- **落点**：`app.js flushPendingSystemMessages`（1372-1377 的过滤链处）或 `supervision-policy.js`。
- **做法**：新增判定——`taskType==="supervision" && source==="random" && dueAt 超 RANDOM_REDELIVERY_MAX_AGE_MS`（默认 **10 分钟**，用户裁决：random 机会型，丢一条马上有新的）→ 丢弃并记日志（沿用 `expired` 事件形态）。**不**做"重放批上限"和"同分钟窗口"（伪目标）。
- **备注**：本次事故触发源（7× CODEBUDDY_START_TIMEOUT）是当日已修掉的权限吊死，触发概率已大降；本步是防下一次运行时故障。
- **验证**：A2。

### 第 3 步｜RC1 路线 B 实施（已裁决，根治）
- **落点**：`system-message-dispatcher.js:30`、`weixin/message-utils.js:47`、thread→session 映射层。
- **关键分析（deepseek v2 缺失）**：分裂初衷大概率是**模式隔离**——system 回合是 "SYSTEM ACTION MODE / 返回 JSON"，weixin 回合是人格聊天；路线 A 合并 scope 会把 JSON 动作交换注入聊天历史。故倾向**路线 B**：已送达的主动消息以**助手角色**镜像写入用户会话（用户亲眼见过这些消息，作为 assistant 历史是诚实的，不动会话生命周期）。
- **过渡**：评审落地周期长时，启用第 3.5 步缓解；P1-5 完成后关闭缓解。
- **验证**：A1 在关闭注入块后仍成立。

### 第 3.5 步｜~~跨 scope 摘要缓解~~（已裁决取消，见 §6 裁决 5）

> 用户裁决：过渡注入不做，只保留内部记录；直接实施第 3 步路线 B。重新打招呼在路线 B 落地后自然消失。
- **落点**：`app.js enrichIncomingMessageWithZhijiantimeFreshRead`（704-727）。
- **做法**：给用户回合追加「本轮之前的主动触达记录」摘要，**来源必须是模型最终送达文本（或剥离 `[Zhijiantime…]`/`[CyberBoss supervision note]` 等已知内部块后的文本）**，限条数、限字数，显式声明"这是助手侧已发出的主动消息"。**禁止直接用队列消息原文**（路径 B 重试过的自带内部块）。
- **验证**：A1 + 注入文本不含任何内部块前缀的断言。

### 第 4 步｜RC6 承诺捕获改为模型判断（D1 再修正，用户裁决版）
- **落点**：`daily-supervisor.js capturePlanningCommitment`（92-134）、`app.js:737-746`、用户回合 prompt 注入点。
- **设计（替代原关键词门槛，用户 2026-09-22 裁决）**：
  1. **主路径 = 模型判断**：awaiting_commitment 态下，注入上下文中明确告知模型"用户若给出了做计划的具体时间，请在回复末尾输出机器可读标记（如 `[PLAN_COMMIT iso-time]`）"。app.js 从模型输出中解析标记 → **时间值再经确定性解析器校验**（`explicit-checkpoint.js` 复用）→ 建 checkpoint。发送前剥离标记。
     - 优点：模型有完整上下文（催办语境、用户措辞、残余任务），"我吃完饭大概八点半去弄指尖时光"这类说法关键词表永远覆盖不全，模型能判。
     - 兜底：模型漏标 → 用户催办态仍在，下一轮随机查岗会再催，用户再说一次即可；所有捕获记日志可复盘。
  2. **确定性兜底路径**：用户消息本体≈纯时间表达（归一化后残余任务文本为空，如裸回 "21:00"）→ 不经模型直接走原 `capturePlanningCommitment`。这是催办模板明确索求的回复形态，必须 100% 可靠，不能依赖模型自觉。
  3. **话术诚实化**：`app.js:742` 的 announcement 从硬编码改为复述解析结果（参照 conversation 路径做法），让误解析裸露。
- **风险**：中。新增"模型必须可靠输出标记"的依赖 → 用确定性路径覆盖主流程（裸时间），模型路径覆盖长尾；标记解析失败有日志。
- **验证**：A6 四组用例（负例 / 裸时间正例 / 意图词正例 / 自然表述正例）。

### 第 5 步｜RC9 承诺状态迁移时机（RC8 已裁决移出范围）

> **RC8 移出**：用户裁决——空计划日高频催办（实测 ~15 次/天）是 ADHD 场景的产品特性，"一天催 15 次不算多"。`lastPromptAt` 只写不读不再视为缺陷，本步不动；如未来需要，按配置项另立小任务。
- **RC9 落点**：`daily-supervisor.js:60-69`、`app.js:2093-2099`。
  - **做法**：`followup_scheduled → awaiting_commitment` 迁移从富化阶段（派发前）移到 `turn.completed/delivered` 之后；失败路径保持原状重试。
  - **配套（D7）**：`:70-75` 闸门改为「state===followup_scheduled &&（followupDueAt 未到 **或** 该消息有未完成的重试 pending）」——否则重试期间 followupDueAt 已过，random 立即复鸣。
  - **验证**：A7。

### 第 6 步｜RC7 重试上限 + 全局过期 + 可观测性（配套，同批）
- **落点**：`app.js:2215-2236`、`supervision-policy.js:152-175`。
- **做法**：supervision 消息 maxAttempts=8（超则 archived，**有记录不静默**）；全局 staleness：dueAt 超 24h 归档；每次主动派发记录 `attempt / supervisionKey / 富化份数 / 是否与用户回合相邻`。
- **风险**：中。上限过低在长时间坏运行时丢消息——可观测性是前置配套，丢必须留痕。
- **验证**：A8。

### 第 7 步｜P2 收尾
- **RC4 拆泡**：文案侧把监督消息压成单段（换行改句号，保留语义）或对 `taskType==="supervision"` 禁用拆泡；**不全局提高阈值**。验证 A4。
- **内部指令分离**：`daily-supervisor.js:400-402` 英文祈使句不再拼进 `message.text`，中期改独立 role（与 P0-4/D5 同一方向，别做两遍）。
- **去重闸门单测**：`planning_followup × random` 并发一条（队列层合并已兜住，仅补回归测试）。
